Mock server

  • View as Markdown
  • Open in ChatGPT
  • Open in Claude

rapidoc mock serves every local spec of the portal on one port, each under /<api id> (a version other than the default under /<api id>/<version>). Readers can press Try before the API exists, and you can demo who may call what with real tokens.

List the mock as a server in the spec, and the reference pages’ Try calls it:

This site’s example API does exactly that: run npm run mock:portal-site in the RapiDoc repository, where this site’s source is, and Try answers. Run workflow on a workflow diagram uses the same server, so whole workflows run with no backend.

What it answers

Section titled “What it answers”

Examples from the spec first, else data generated from the schema; requests are validated against the spec; Prefer headers pick a documented response (Prefer: code=404); CORS is allowed for any origin. All of that, streamed responses (OpenAPI 3.2 itemSchema: Server-Sent Events and JSON Lines, sent one item at a time), and the options (--port, --host, --seed, --stream-interval), is on the Mock Server page of the RapiDoc docs.

Real token checks

Section titled “Real token checks”

Each operation’s security is enforced. Start the mock with your OpenID Connect issuer, and bearer tokens must be signed by it, unexpired, for your audience and carry the operation’s scopes (else 401 or 403):

--issuer and --audience can also come from RAPIDOC_MOCK_ISSUER and RAPIDOC_MOCK_AUDIENCE. Without --issuer, any bearer token passes and scopes aren’t checked. Combined with Try with the reader’s token, signed-in readers see 200 or 403 depending on their own permissions.

Without a portal

Section titled “Without a portal”

The mock also works on plain spec files:

Each spec is served under its file name: orders-api.yaml is /orders-api. The mapping is printed at start. This needs only @rapidoc/cli and @rapidoc/mock, not the portal.
